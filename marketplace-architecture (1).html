Catalog & compatibility
Make · CarModel · Generation · Modification · ItemCompatibility · UserCar
📖
The four-level hierarchy and why each level exists
Make · CarModel · Generation · Modification
▶

Make — The manufacturer. Toyota, BMW, Ford. ~50 rows total. Never changes.

CarModel — The consumer product name. Supra, Tacoma, 3 Series. Belongs to a Make. This is purely a marketing label — "Supra" means nothing mechanically without knowing the generation.

Generation — The chassis entry. This is the real fitment anchor. MA70 Supra, JZA80 Supra, E82 BMW 1 Series Coupe. Each row has a production_start and production_end as full dates (stored as first day of the month, e.g. 1986-01-01). chassis_codes is an array — ["MA70"] for simple cases, ["DB03","DB23","DB43"] when the catalog groups multiple codes that are mechanically identical. Two MA70 generations (1986–1988 and 1988–1993) are two separate rows because the catalog treats them as distinct — that date boundary usually marks a facelift or technical update that affects parts.

Modification — The deepest atom. One row per exact production configuration. TZNA40L-PRZSZA is a specific Tacoma: automatic, 8-speed floor shift, double cab, from December 2023. This level matters for engine-specific parts (alternators, intake manifolds) and configuration-specific parts (transmissions). For body parts — a door panel — the Generation level is enough.

The compatibility level decision
ItemCompatibility has a compat_level field — "generation" or "modification" — so you know how broadly a match applies

A door handle fits the whole E82 generation — every engine, every trim. That compatibility record has compat_level = generation and modification_id = null. When any buyer with any E82 variant checks, it matches.

A specific engine alternator (N52N engine only) fits only Modifications that have engine_code = N52N. That compatibility record has compat_level = modification and points to specific Modification rows. A buyer with an N54 E82 does NOT get a match.

The year_from and year_to fields on ItemCompatibility let you express sub-ranges within a generation. For example, a headlight that changed design in mid-production: "fits E90 sedan, but only from 2008 onward." Generation ID is set, modification_id is null, year_from = 2008.

Buyer's saved cars — UserCar
Buyers can save multiple cars. Each has a generation + optional modification + exact year.

When a buyer registers, they can add their car(s) via the Make → CarModel → Generation → Modification cascade. They also enter their exact production year (because a Generation spans multiple years and the year matters for sub-range compatibility). They can save a nickname ("daily driver", "project car") and mark one as default for the main compatibility check.

The compatibility check at browse time: SELECT * FROM ItemCompatibility WHERE generation_id = [buyer's generation] AND (modification_id IS NULL OR modification_id = [buyer's modification]) AND (year_from IS NULL OR year_from <= [buyer's year]) AND (year_to IS NULL OR year_to >= [buyer's year]) AND is_verified = true. If a row is found → green "Fits your car" badge. If not → "Compatibility unknown."

Buyer's modification also eliminates checkout questions. If the buyer saved their modification (they know they have an N52N engine), the system already knows the answer to "what engine is your car?" — no question is shown at checkout for engine-specific options.

AI research process
Vehicle → Variation → Item → ItemOptionConfig → Option → ItemCompatibility → ItemPhoto
1️⃣
Seller uploads vehicle → Vehicle row created, photos stored
Vehicle · VehiclePhoto
▶

Seller picks Make → CarModel → Generation from the catalog. Optionally drills down to Modification if they know their exact config. Fills in year (exact production year), vin, color, mileage, condition, and critically seller_zip (needed for shipping quotes). Uploads photos of the car. Each photo → one VehiclePhoto row with sort_order and label (front, rear, engine bay, interior). Vehicle status = pending_research. AI job is queued. Zero Item rows exist yet.

2️⃣
AI builds the research checklist from categories + options
Category · OptionCategory · Generation · Modification
▶

System reads the full Category tree with all OptionCategories attached. It also reads the vehicle's Generation and Modification (if set). The Modification gives the AI the engine code, transmission type, cab type, drive type — all the specific properties of this vehicle that will drive option elimination. This combination becomes the research checklist: for every part category, what are all theoretically possible options, and which ones can already be ruled out from the vehicle's known specs?

3️⃣
AI confirms parts, eliminates options, creates Variations + ItemOptionConfig
Variation · Option · ItemOptionConfig
▶

For each confirmed part, the AI creates a Variation draft. Then it creates all possible Option rows — and immediately marks the invalid ones with is_ai_eliminated = true plus an elimination_reason. Example: "Vehicle Modification has engine_code = N52N. Options for engine sizes B46/N51/N54 are eliminated."

After elimination, the AI creates one ItemOptionConfig row per OptionCategory that applies to this item. It counts the surviving options and sets surviving_count. If surviving_count = 1, is_buyer_question = false — the answer is already known. If surviving_count > 1, is_buyer_question = true — the buyer must answer at checkout. This flag is per-item per-option-category, not global, which is the fix from v3.

All photos the seller uploaded are now analyzed by AI per-part: it picks the best matching vehicle photos for each item and creates ItemPhoto rows automatically. Seller can add more or reorder later.

4️⃣
AI compatibility pass — generation or modification level per part
ItemCompatibility · compat_level
▶

For each confirmed part the AI determines: does this part's fitment depend on engine or transmission? If yes → compatibility records are at compat_level = modification, pointing to specific Modification rows with the right engine code. If no (body panel, trim piece, glass) → compat_level = generation, covering all Modifications under this Generation.

The AI also cross-references the catalog database to find other generations this part fits. A 2JZ-GTE alternator might fit JZA80 Supra, JZZ30 Soarer, and JZX100 Chaser — all share the same engine. Each confirmed match gets an ItemCompatibility row: source = ai, is_verified = false initially, confidence_score set.

Auto-verification threshold: rows with confidence_score ≥ 0.85 → is_verified = true automatically. Below 0.85 → sits in human review queue. Source = oem_data rows always auto-verify (they come from the authoritative catalog).
5️⃣
Variations approved → live Items created → seller notified
Item · status = active · seller analytics report
▶

After review, Variation review_status = approved. System creates a real Item row. Status = active. ItemCompatibility rows already point to it. shipping_size is auto-calculated from dimensions using the size rules. oem_part_number is populated from catalog data if available.

Seller receives notification + analytics report: part count, estimated total revenue, highest-demand parts, recommended pricing, packaging tutorial per shipping size category. Vehicle status = active.

Options, elimination & buyer questions
OptionCategory · ItemOptionConfig · Option · UserCar.modification_id
🔍
Full flow: from vehicle specs to buyer question (or no question)
Modification → Option elimination → ItemOptionConfig → checkout
▶
Step 1 — AI reads vehicle specs

AI reads engine_code, transmission_type, drive_type from the vehicle's Modification. These are the facts it uses to eliminate impossible options.

Step 2 — All options created, invalid ones eliminated

For an alternator on a BMW E82 128i with N52N engine: OptionCategory "Engine" has possible values N51, N52N, N54, N55. AI creates four Option rows. N51 → eliminated (wrong engine family). N54 → eliminated (turbocharged, different alternator). N55 → eliminated (different generation). N52N → is_ai_eliminated = false. One survives.

For a car that came with BOTH N51 and N52N (some markets): both survive elimination. Now the buyer must answer. ItemOptionConfig for this item's "Engine" category: surviving_count = 2, is_buyer_question = true.

Step 3 — At checkout, buyer sees only required questions

System reads ItemOptionConfig rows for the item where is_buyer_question = true. For each one, it shows the buyer the surviving (non-eliminated) options from the Option table. Buyer picks. Their answers are saved in OrderItem.selected_options JSON.

If the buyer has a UserCar with a modification_id saved, the system cross-checks: does their modification's engine_code match one of the surviving options? If yes → answer is pre-filled and the question is skipped. The buyer gets a smoother checkout and fewer clicks.

Bundle rules
BundleCategory · Bundle · BundleItem · Item.status
🏗️
Assembly bundles — sell whole, break apart only if damaged
type = assembly · status = hidden_in_assembly
▶

When AI confirms all sub-parts of an assembly template exist and are in good condition, a Bundle is auto-created. Sub-items get status = hidden_in_assembly — invisible as individual listings. Only the bundle listing shows. If any sub-part is damaged: bundle → disbanded, good sub-parts → active individual listings, damaged part → removed or for_parts condition.

🎁
Discount bundles — auto-create alongside individual listings, auto-disband as items sell
type = discount · three disband rules
▶

When all items matching a discount template are active, a Bundle is created alongside them. Individual items still show separately. Three auto-disband rules trigger on any item status → sold:

Rule 1 — Whole bundle purchased: all items → sold, bundle → closed.

Rule 2 — One item sells individually: remove from BundleItem, recalculate discount for remaining count.

Rule 3 — Bundle drops to 1 item: delete the bundle. Last item becomes a normal standalone listing.

Runs as a DB trigger or background job on every Item.status change to "sold".

Orders & payments
CartItem · Order · OrderItem · Payment
🛒
Cart → checkout → order → payment capture
CartItem · Order · OrderItem · Payment
▶
Adding to cart

Buyer clicks "Add to cart" → one CartItem row per item. No quantity field — each item is one unique physical part. You can't buy two of the same item because only one exists.

Checkout — buyer questions answered

For each CartItem, system reads ItemOptionConfig rows where is_buyer_question = true. Buyer answers each question (engine size, side, etc.) unless their saved UserCar already answers it. Answers collected in memory until order placement.

Order placed

One Order row created. One OrderItem per cart line — stores price_at_purchase, full item_snapshot JSON, and selected_options JSON (buyer's checkout answers). Order stores vehicle_snapshot. All CartItem rows deleted.

One Payment row created immediately with status = pending. Payment provider is called. On success: status = captured, paid_at set, provider_reference stored (Stripe charge ID etc.). On failure: status = failed, Order stays pending, buyer is shown an error and can retry.

Refunds

When a dispute resolves with a refund: Payment.refunded_amount is updated, Payment.status → refunded (full) or partial_refund, refunded_at set. The refund goes through the same payment provider reference. Full audit trail preserved.

🚚
Shipping flow
ShippingRequest — all manual, no API
📦
From order placed to part delivered — full manual flow
ShippingRequest · Item.shipping_size · origin_zip · dest_zip
▶
Size already known at item creation

When an Item is created from a Variation, shipping_size is auto-calculated: system reads weight_lbs + dim_l_in + dim_w_in + dim_h_in and applies the upgrade rules in order (Small → Medium → Large → Extra Large). Result stored on Item. Buyer sees the size category and estimated cost at browse time before even adding to cart.

After payment — ShippingRequest created

For each OrderItem that isn't pickup, one ShippingRequest row is created. It copies origin_zip from Vehicle.seller_zip and dest_zip from the buyer's ShippingAddress. Support team sees a queue of open ShippingRequests.

Pickup — buyer gets a confirmation code. Shows up at seller's location. Support marks delivered when confirmed. 30-day quality guarantee starts.

Parcel (Small/Medium) — support contacts USPS/FedEx/UPS, gets actual quote, stores as actual_cost, purchases label, saves as label_url, emails to seller. Seller prints, attaches, drops off. Tracking number entered manually.

Freight (Large/Extra Large) — support contacts freight carriers manually, arranges pickup, enters tracking. For engines/transmissions: pallet arrangement included.

Delivery confirmed

Carrier confirms delivery → support sets is_delivered = true and delivered_at on ShippingRequest. Order status → delivered. Buyer notified. Prompted to leave SellerReview (linked to the specific OrderItem, not just the seller).

Opening a dispute

Buyer clicks "Open dispute" on a delivered OrderItem. They pick a reason (not_as_described, wrong_part, not_received, damaged, other) and write a description. A Dispute row is created: status = open. Seller and admin are notified immediately.

Evidence phase

Buyer, seller, and support all post DisputeMessage rows. The sender_role field (buyer/seller/support) keeps it clear who said what. Buyers and sellers can attach photos as attachment_url — pictures of the part, damage, packaging. Dispute status → under_review.

Admin resolution

Admin reviews the full DisputeMessage thread and both the item_snapshot and vehicle_snapshot from the OrderItem/Order. They pick a resolution:

resolved_refund — buyer gets money back. Admin sets refund_amount, marks return_required if part must come back. Payment.refunded_amount updated, Payment.status → refunded or partial_refund.

resolved_return — buyer returns the part, gets refund after. ShippingRequest created in reverse direction.

resolved_no_action — dispute not valid. Explained in resolution notes. Case closed.

Admin fills resolution text, sets resolved_by (their user ID), sets resolved_at. Dispute status → closed. Both parties notified.

The item_snapshot on OrderItem is what makes disputes fair. It's a frozen copy of exactly what was listed — title, description, options, photos at checkout time. Seller can't edit the listing after sale to cover their tracks. Admin always sees exactly what the buyer was promised.

Thread · Message
▶

Buyer clicks "Message seller" on a listing → one Thread row created with buyer_id, seller_id, item_id. All messages are Message rows with sender_id and is_read flag. Different item = new thread. last_message_at on Thread is updated on every new message — used to sort the inbox by most recent activity. Simple private inbox, no AI, no automation.
